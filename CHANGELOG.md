## [Unreleased]

### Added

- P0 repo setup: `docs/SPEC.md`, `CLAUDE.md`, `.env.example`, `docker-compose.yml` (PostGIS 17-3.5, Valkey 8.1, `atk_test` database for tests), `README.md`, `render.yaml`, CI workflow and PR template.
- P1 server skeleton: Express 5 (ESM, run with tsx), Zod-validated `config/env.js`, Prisma 7 client with `@prisma/adapter-pg` (`db` + `readDb`), ioredis connections for cache and BullMQ, winston logger, `ApiError`/`ApiResponse`, error handler, Redis-backed global rate limit (passes through while Redis is down), `/health` (503 on DB down, `redis: "degraded"` on Redis down), graceful shutdown for API and worker, BullMQ worker with an empty processor registry, Vitest + Supertest setup.
- P2 database: Prisma schema from Part 5 §3, first migration with PostGIS, pg_trgm, GiST/GIN/trigram/partial indexes and the `searchVector` trigger, `services/geo.js` (distance query and point writers), idempotent seed (super admin, 10 groups, 60 directory and 9 market categories with Nepali names, 16 areas with centre points, plans, settings, home sections, synonyms, 49 DRAFT brand/app/place stubs and 4 LIVE emergency numbers), tests for distance ordering, the search trigger and seed idempotency.
- P3 auth: `/auth` routes from Part 6 §3. Registration with email verification, login with progressive lockout (5 failures, then 15 min doubling up to 24 h), rotating refresh tokens stored as SHA-256 hashes with reuse detection (reuse revokes every session), logout and logout-all, password reset (revokes all sessions), TOTP 2FA required for Moderator and above (setup, enable, verify; secrets AES-256-GCM encrypted; codes cannot be replayed), optional Google sign-in, Turnstile check on register. No account enumeration on register, resend-verification and forgot-password. Middleware: `verifyToken` (re-reads session and user), `optionalAuth`, `requireRole` (staff hierarchy, 2FA enforced), `requireOwnership`, `validate`. Emails go through the BullMQ `email` queue; without SMTP the worker logs them.
- P4 client foundation: Next.js 16.4 (App Router, JavaScript, Turbopack), Tailwind 4 with the Part 4 §6 tokens in `@theme` (placeholder colours, light and dark, all text pairs at least 4.5:1), TanStack Query provider, `services/api.js` (one axios instance, access token in memory, one refresh on 401 with a request queue and a cross-tab Web Lock), Zustand auth store, `proxy.js` guarding `/account`, `/business`, `/admin`, auth pages (login with the 2FA setup and verify steps, optional Google button, register with Turnstile, verify email, resend, forgot and reset password), English/Nepali toggle (both languages in the static HTML, switched by `<html data-lang>`), `layout.js`, `robots.js`, `sitemap.js`, `not-found.js`, `error.js`.
- P5 directory API: `/public` home, groups, categories, category listings (area, tags, open now, price, rating, distance; cursor pages with at most 2 Featured cards on top), listing detail (media and offers only when Featured), reviews, similar, search (full text with prefix matching + trigram + two-way synonyms, area filter, distance ranking, matching categories, did-you-mean), suggest, areas, plans, public settings and track. `cache.middleware` stores public GETs in Redis with tags (`home`, `groups`, `category:<id>`, `listing:<id>`, `search`, …) and skips caching for visitor locations and when Redis is down. Track counts go to Redis (repeat views deduped for 30 min, Nepal dates) and a worker job flushes them to `listing_stats_daily` every 5 minutes. Worker jobs keep `categories.liveCount`, `businesses.searchExtra` and `profileScore` current every 10 minutes.
- P6 public pages: Home (search with area picker and every homepage-builder section), Group, Category (tag chips, area, open now, price, rating, near me, list/map, load more; filters kept in the URL), Listing detail (action bar, hours in 12-hour Nepal time, lazy map, Featured photos/videos/offers, reviews, Report wrong info, similar nearby, LocalBusiness JSON-LD) and Search (results grouped by category, matching categories, did-you-mean, near me, map). Server components with `generateMetadata` and ISR (1 h fallback) tagged `home`, `groups`, `areas`, `settings`, `category:<slug>`, `listing:<slug>`; `/api/revalidate` (secret, `revalidateTag(tag, 'max')`) and a worker `revalidate` queue that sends id and slug tags. Header, mobile bottom bar, footer with emergency numbers, offline notice, skeleton/empty/error states. API: `POST /public/reports` (guests with Turnstile), map pins and hours on cards, `text/plain` track beacons, `Cross-Origin-Resource-Policy: same-site`.
- P7 admin panel: admin API from Part 6 §7 (see the P7 server commit) and the web admin at `/admin`: separate admin login with the TOTP step (`/admin/login`), role-aware sidebar, dashboard (pending queues, live/draft counts, users, revenue this month, clear site cache), listings table with search, status filter, bulk status and CSV import with live job status, listing form (categories with primary, tags, contacts, area, map point, weekly hours editor, SEO, owner assignment, delete), claims/reviews/reports queues with bulk actions, categories tree and homepage sections with drag-and-drop (mouse, touch and keyboard), tags, areas, synonyms, CMS pages with a Tiptap editor, draft/publish and preview, SEO for groups and categories, settings (emergency numbers, contact, social links), plans, payments, users (suspend, roles for super admins) and the audit log. Public `/about`, `/contact` (form with Turnstile), `/terms`, `/privacy`, `/refund` render published CMS pages.
- P8 business portal: API from Part 6 §5 (see the P8 server commit) and the web portal at `/business`: dashboard with 30-day views, calls, WhatsApp, directions and website clicks (day by day), listing details (owner fields, logo upload, weekly hours, area, address and map pin with a click-to-place map or current location), photos and videos (Featured only, plan limits, alt text required, drag to reorder), offers (Featured only), plan and history, invoices, and a listing switcher for owners with several listings. Members see how to claim a listing (with an optional proof photo) or submit a new business. Public listing pages link to the claim flow while a listing has no owner. Admin: media library.
- P9 payments: `/payments` routes from Part 6 §6 for Khalti (KPG-2 initiate and lookup) and eSewa (ePay v2 signed form and status check). The price comes from `plans` only; a plan activates in one transaction (payment COMPLETED with an invoice number, subscription ACTIVE, `featuredUntil`, audit row) only after the server checks status and amount with the gateway; a repeated verify returns the existing result; an amount mismatch fails the payment; a renewal starts when the current period ends. Worker `subscriptions` queue, hourly: expire ended plans (clearing or lowering `featuredUntil`), close checkouts abandoned for a day, and send renewal reminders 7 days and 1 day before expiry (once each). Business portal: Khalti and eSewa buttons on the plan page and return pages under `/business/plan/return/` (Khalti, eSewa success and failure).
- P10 member area: `/me` routes from Part 6 §4 (market follows in P11): profile (name, phone), password change (signs out other devices; accounts created with Google can set a first password), devices list with sign-out per device, saved listings (cursor pages of listing cards, newest first), reviews (one per member per listing, never on your own listing; new and edited reviews wait for moderation and an edited or deleted approved review leaves the rating at once), and account deletion. Web: `/account/profile`, `/account/saved` and `/account/reviews` in English and Nepali, plus Save and Write a review on listing pages (logged-out visitors are sent to log in and back).
- P11 events and marketplace (phase 2). Events: public calendar `GET /public/events` (from today in Kathmandu, area and date filters, cursor pages) and `GET /public/events/:slug`; submissions from members (`/me/events`) and owners for their listing (`/business/listings/:id/events`), each with a status list, an optional cover image and map pin; moderation (`/admin/events`: approve, reject, edit, delete). Marketplace: `GET /public/market` (category, condition, price range, area, title search), `GET /public/market/:slug` and market categories; members post, edit (back to moderation), mark sold and delete items with up to 6 photos (`/me/market`); moderation (`/admin/market`); an hourly worker job takes items down 30 days after approval and emails the seller once. Web: `/events`, `/events/[slug]` (Event JSON-LD), `/market`, `/market/[slug]` (Call and WhatsApp only), `/account/market`, `/account/events`, `/business/events`, `/admin/events`, `/admin/market`, and event cards on the home page.
- P12 hardening (see `docs/HARDENING.md`). Sentry on the API, worker and web app (server rendering, and a browser SDK loaded on idle or on the first error, so it is not in the first page load); errors only, no personal data, off without a DSN. Security headers on the web app (HSTS, nosniff, frame denial, referrer and permissions policies, production allowlist CSP). k6 load test `server/scripts/load-test.js` (50 visitors, p95 < 300 ms). Weekly encrypted `pg_dump` to a GitHub Actions artifact kept 90 days (`.github/workflows/backup.yml`). Accessibility, rate-limit, CORS, cookie and robots review, and the Part 8 §6 launch walkthrough.

### Notes

- `render.yaml` keeps secrets as `sync: false` on each service because Render does not allow `sync: false` inside an environment group, and uses Render's current plan IDs (`1c-2g`, `0.5c-512mb`, `256mb`).
- `postgis/postgis` has no arm64 image, so local Postgres runs as `linux/amd64`.
- `prisma`, `@prisma/client` and `@prisma/adapter-pg` pinned to 7.10.1 (npm `latest` for `prisma` points at an 8.0 release candidate). `@prisma/client` is required at runtime by the `prisma-client` generator output.
- `ioredis` pinned to 5.11.1, the version BullMQ 6 is tested against (ioredis 6 switched to RESP3 by default).
- Tests use the `atk_test` database and Valkey logical DB 1.
- An area filter keeps app and hotline listings (they have no area and serve the whole valley).
- `profileScore` (0 to 100) is computed by the worker from logo, description, contact, website, hours, map pin and area; it orders results when the visitor's location is unknown.
- Featured placements on category pages rotate hourly; with a location they are ordered by distance.
- Performance (Part 4 §9), measured locally on the production build: initial JS 157–168 KB gzip on home, group, category, listing and search pages; Lighthouse mobile performance 98, accessibility 100, best practices 100, LCP 2.3 s on home, category, listing and search. To get there, client components only ship the UI text they use (`lib/messages/client.js`; server-only text renders through `ST`), public images are plain `<img srcset>` with Cloudinary transformations (`CloudImage`) instead of `next/image`, and axios, the report form and the filters sheet load on first use. The login page is 229 KB (react-hook-form + Zod on the auth pages).
- Admin users: admins list and suspend members and business owners; only super admins change roles or staff accounts (Part 6 §7 over Part 3 §7). Role changes and suspensions sign the user out everywhere.
- CSV import (`POST /admin/listings/import`) runs once in the worker (no retries, so partial progress never duplicates rows); `GET /admin/listings/import/:jobId` reports the result.
- CMS pages are limited to the five pages with public routes (about, contact, terms, privacy, refund).
- The admin UI and the business portal are English only; the Nepali toggle covers the public site.
- Uploads: the API chooses each file's Cloudinary public_id and signs it, then reads the uploaded file back from Cloudinary (size, format, URL) before saving, so the browser cannot claim another listing's file or skip the size cap. Listing videos are YouTube or Instagram Reels links. Claim proofs are images.
- `GET /me/claims` (not in Part 6 §4) lets members see their claim status. A "List your business" submission is PENDING with the member as owner; when Admin sets it LIVE the member becomes a business owner.
- ISR tags use slugs on pages (pages are routed by slug); the worker always sends both the id and slug forms.
- Client pins `@hookform/resolvers` 5.9.2: 6.0.0 has conflicting optional peer dependencies on `effect`. Client ESLint resolves to 9.x because some plugins in `eslint-config-next` do not declare ESLint 10 yet (both are supported by Next.js).
- The five raw-SQL indexes from Part 5 §4 are also declared as `@@index` in the schema (same names and types) so `prisma migrate dev` sees no drift and never proposes dropping them. The partial index and the search trigger stay raw SQL only.
- New env variable `TOTP_ENCRYPTION_KEY` (32 bytes, base64) encrypts admin TOTP secrets at rest; added to `.env.example`, `render.yaml` and CI.
- The API also sets an `atk_session=1` hint cookie on the web app's domain at login and refresh (cleared on logout). `proxy.js` uses it to redirect logged-out visitors and the browser uses it to skip the refresh call for anonymous visitors, so it is readable by JavaScript; it carries no credentials.
- Seed rows are created only when missing, so re-running the seed never overwrites Admin edits. Seeded listings carry no contact details except the public emergency numbers. Uber is included: it launched in Kathmandu Valley in mid-2026.
- eSewa's documented signature example does not match its own input, so signing was checked against the eSewa UAT form endpoint instead (a correct signature opens the payment page, a wrong one gets 400) and the status check against the UAT status endpoint. The production eSewa URLs are in `render.yaml`; production refuses sandbox payment settings (`dev.khalti.com`, the `rc`/`rc-epay` eSewa hosts, `EPAYTEST`).
- Invoice numbers are `ATK-YYYYMMDD-` plus 8 characters of the payment id.
- Not yet run end to end: a completed Khalti sandbox payment (needs a Khalti test secret key in `server/.env`) and a completed eSewa UAT payment (needs a login to eSewa's test wallet). Both gateways' verify paths are covered by tests with the gateway responses stubbed.
- Account deletion is a soft delete confirmed with the password and the word DELETE: name, email (replaced so the address can register again), phone, password, Google link and 2FA are cleared, sessions revoked, saved listings removed, pending claims rejected, owned listings unassigned (paid plans stay with the listing) and a `user.delete` audit row written. Reviews stay and show as "Former member". Staff accounts cannot delete themselves; a super admin removes the staff role first.
- `GET /me/saved` also takes `?businessId=` so the Save button can show whether a listing is saved. Changing the password and deleting the account share a limit of 5 attempts per 15 minutes per account; posting and editing reviews count toward the existing 10 per hour submissions limit.
- JS budget re-measured after the Save and review buttons: home 162 KB, listing 167 KB, search 168 KB gzip. The review form, its text and the API client load only when needed.
- Phase 2 decisions (asked and confirmed): members and business owners both submit events (Part 3 §6), so `/me/events` was added next to `/business/listings/:id/events`, with `account/events` and `business/events` pages; the market item page is `market/[slug]` to match `GET /public/market/:slug` (Part 3 §13 says `[id]`); events get a detail page `events/[slug]`; market items take up to 6 photos (JPG, PNG or WebP, 5 MB, alt text required) and events one optional 5 MB cover image.
- Market items are live for 30 days from approval; any edit takes the item down until it is approved again, and sold items cannot be edited. Deleting an account also removes the member's market items (they carry their phone numbers).
- Event times are entered and shown in Kathmandu time whatever the device's time zone.
- Fixed: the map pin's latitude and longitude boxes (business portal and event form) dropped a typed decimal point.
- Photo and cover uploads were not run in a browser here because the local API has no Cloudinary keys; the API tests cover them with Cloudinary's lookup stubbed.
- JS budget after P11: home 162 KB, market 164 KB, events 163 KB, event and item pages 160 KB, listing 168 KB, search 168 KB gzip. Market and events text lives in `lib/messages/market.js` and their date helpers in `lib/dates.js` so other pages do not ship them.
- P12 decisions (asked and confirmed): the browser Sentry SDK loads lazily to keep the JS budget; backups go to GitHub Actions artifacts (secrets `DIRECT_URL`, `BACKUP_PASSPHRASE`); the load target is 50 concurrent visitors with p95 under 300 ms and under 1% errors.
- Fixed in P12: listing pages, search result headings and breadcrumbs linked to categories with fewer than 5 live listings (no public page yet, so 404); cards and listing details now carry `category.isPublic`. The event page's details list markup was corrected.
- Local k6 run: p95 4.0 ms overall (home 1.9, category 2.1, listing 2.0, search 5.2 ms), 0 errors in 5,668 requests. These figures have no network latency; rerun against production before launch.
- JS budget with a Sentry DSN set: home 162 KB, listing 168 KB, search 169 KB, market 164 KB, events 164 KB gzip.
- Browser error reports are dropped by visitors' ad blockers (they block Sentry's ingest URLs); Sentry's `tunnel` option would route them through the site and was not added.
